01

Repository (repo)

The project folder tracked by Git — your local working tree plus the hidden history Git stores — and usually mirrored on a host like GitHub.

Animation: a project folder with working files gains a hidden .git history store, then mirrors to GitHub as origin.

A repository is a project folder that Git tracks

Considerations

  • Initialize once per project; don’t nest repos unless you intend to use submodules.
  • Keep secrets out of the repo; use .gitignore and environment variables.
  • Agree early on a default branch name and hosting remote.

02

Clone

Download a full copy of a hosted repository to your machine, including history and remote tracking branches, so you can work offline and sync later.

Animation: git clone copies a remote GitHub repository onto your laptop, including history and an origin remote.

The repository lives on GitHub

Considerations

  • Cloning large histories can take time; shallow clones help when you only need recent work.
  • You’ll get a remote named origin by default — know where it points.
  • Clone the repo you intend to contribute to, not a fork, unless you plan to open a PR from a fork.

03

Branch

A safe parallel timeline of commits. You can experiment or ship a feature without disturbing the main line of history until you’re ready to combine them.

Animation: a feature branch forks from main so new commits leave the shared history untouched.

main holds the project’s shared history

Considerations

  • Name branches for intent: feature/…, fix/…, chore/….
  • Keep branches short-lived so merges stay small and reviewable.
  • Update from main regularly to avoid painful catch-up later.

04

Commit

A snapshot of staged changes plus a message that explains why those changes exist. Commits form the history you can review, revert, or rebuild from.

Animation: edited files are staged with git add, then saved as a commit snapshot with a message.

Edit files in your working directory

Considerations

  • Write messages for future readers: what changed and why, not only what files.
  • Prefer small, focused commits over one giant “misc fixes” blob.
  • Don’t rewrite shared history on protected branches without team agreement.

05

Push / Pull

Push uploads your local commits to the hosted repository. Pull downloads remote updates and integrates them into your current branch.

Animation: git push uploads local commits to origin; git pull brings a teammate’s remote commit down.

You made two new commits locally

Considerations

  • Pull (or fetch + merge/rebase) before pushing when others share the branch.
  • Never force-push to shared default branches unless your team’s process allows it.
  • Know whether your pull merges or rebases — the result looks different in history.

06

Diff

The visual difference between two versions of code — often between branches, commits, or your working tree and the last snapshot — line by line.

Animation: two file versions are compared line by line; removed lines are marked with minus and added lines with plus.

Take two versions of the same file

Considerations

  • Read diffs before committing so you don’t ship debug leftovers.
  • Whitespace and formatting changes can drown out real logic changes.
  • Review tools highlight adds and deletes; understand both sides of a change.

07

Merge

Combine one branch into another, preserving both histories and usually creating a merge commit when the branches have diverged.

Animation: diverged feature and main branches join through a merge commit that preserves both histories.

Two branches share a common ancestor

Considerations

  • Merging into main should follow your review process (often via PR).
  • Merge commits make the join point explicit — useful for release archaeology.
  • Resolve conflicts carefully; a clean merge still needs a quick smoke test.

08

Rebase

Replay your commits on top of the latest main so your branch history looks linear, as if you started from the newest base.

Animation: feature commits are replayed onto the latest main commit to form a linear history.

feature started from commit B

Considerations

  • Great for cleaning a private feature branch before review.
  • Avoid rebasing commits already pushed and shared — it rewrites history.
  • Conflicts still happen; you resolve them commit-by-commit during the replay.

09

Merge conflict

Two changes touched the same lines (or nearby structure) and Git can’t choose automatically — you decide the final combined result.

Animation: conflicting edits collide; conflict markers appear; you choose the final line and mark it resolved.

You and a teammate changed the same line

Considerations

  • Communicate with whoever wrote the other change when intent isn’t obvious.
  • After resolving, run tests; conflicts can hide subtle logic mistakes.
  • Smaller, frequent integrations reduce how often conflicts appear.

10

Pull Request (PR)

A request to review and merge your branch into another — the social layer over Git that hosts discussion, checks, and approval.

Animation: a pull request gathers checks and approval, then merges a feature branch into main.

Open a pull request to propose merging your branch

Considerations

  • Describe the why, link issues, and call out risky areas for reviewers.
  • Keep PRs reviewably sized; giant diffs slow feedback and hide bugs.
  • CI, lint, and required reviews exist to protect main — treat failures as signals.

11

Issue

A ticket for a bug, feature, or task. Issues capture context and discussion; they don’t change code until someone opens a branch and PR to address them.

Animation: an issue moves from open to in progress with a branch and pull request, then to done when merged.

An issue describes a bug, feature, or task

Considerations

  • Write a clear title, steps to reproduce (for bugs), and acceptance criteria.
  • Label and assign so the backlog stays navigable.
  • Link issues to PRs so history shows what work closed what ticket.
